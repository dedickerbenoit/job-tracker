## Vulnerabilites identifiees

### [SEC-001] Dependances npm avec vulnerabilites connues (Axios, Vite)

**Severite** : Elevee

**Localisation** :

- Fichier : `frontend/package.json`
- Packages : `axios` (1.x <= 1.15.1), `vite` (8.0.0-8.0.4)

**Description** :
`npm audit` remonte 8 vulnerabilites dont 2 de severite haute :

- **Axios** (15 CVEs) : prototype pollution gadgets, SSRF via NO_PROXY bypass, header injection, XSRF token leakage cross-origin, CRLF injection, DoS par recursion. Beaucoup de ces CVEs sont exploitables si l'application manipule des entrees utilisateur dans les configs Axios ou si un attaquant controle le prototype Object.
- **Vite** (3 CVEs) : path traversal sur les `.map` files, bypass de `server.fs.deny`, lecture arbitraire de fichiers via WebSocket. Impact en **dev uniquement** (serveur de dev Vite), mais important si un dev expose son port 5173.

**Impact** :

- Axios : un attaquant pourrait manipuler les requetes HTTP via prototype pollution si `Object.prototype` est empoisonne par une autre dependance. Le XSRF token leakage pourrait exposer le token CSRF cross-origin.
- Vite : en dev, un attaquant sur le meme reseau pourrait lire des fichiers arbitraires du systeme de fichiers du developpeur.

**Recommandation** :

```bash
cd frontend && npm audit fix
```

Mettre a jour Axios vers >= 1.15.2 et Vite vers >= 8.0.5. Pas de breaking changes attendus.

**Priorite** : P1

### [SEC-002] CSP trop restrictive sur le backend, absente sur le frontend SPA

**Severite** : Moyenne

**Localisation** :

- Fichier : `backend/app/Http/Middleware/SecurityHeaders.php:20`
- Fichier : `frontend/index.html` (pas de meta CSP)

**Description** :
Le middleware SecurityHeaders definit `Content-Security-Policy: default-src 'self'` sur toutes les reponses. C'est correct pour les pages servies par le backend, mais le SPA React necessite des ajustements :

- Les styles inline generes par les composants UI (shadcn/ui, Tailwind) seront bloques sans `style-src 'unsafe-inline'` ou nonces.
- Le SPA est servi via `spa.blade.php` dans le Docker build, donc le CSP du backend s'applique.
- En pratique, si le CSP bloque des elements du SPA, ca se manifeste par des composants sans style.

Note : le frontend servi par Vite en dev n'est pas affecte (pas de middleware backend).

**Impact** :

- Fonctionnel : composants SPA potentiellement casses en production.
- Securite : si le CSP est assoupli navement avec `unsafe-inline`, la protection XSS est degradee.

**Recommandation** :
Utiliser un nonce-based CSP ou bien adapter le CSP pour le SPA :

```php
// SecurityHeaders.php — differencier SPA et API
if (str_starts_with($request->path(), 'api/')) {
    $response->headers->set('Content-Security-Policy', "default-src 'none'; frame-ancestors 'none'");
} else {
    // SPA pages — Tailwind/shadcn needs inline styles
    $response->headers->set('Content-Security-Policy',
        "default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'");
}
```

**Priorite** : P2

### [SEC-003] Session cookie sans flag `secure` en production par defaut

**Severite** : Moyenne

**Localisation** :

- Fichier : `backend/config/session.php:172`

**Description** :
La config session definit `'secure' => env('SESSION_SECURE_COOKIE')` sans valeur par defaut. Si la variable d'environnement n'est pas definie, la valeur est `null`, ce qui signifie que le cookie de session est envoye en clair sur HTTP.

Le `.env.example` definit bien `SESSION_SECURE_COOKIE=true`, mais rien ne garantit que la variable est definie en production si l'operateur cree le `.env` manuellement.

**Impact** :
Si deploy sans `SESSION_SECURE_COOKIE=true`, le cookie de session peut etre intercepte en clair par un attaquant man-in-the-middle.

**Recommandation** :
Ajouter un defaut securise :

```php
'secure' => env('SESSION_SECURE_COOKIE', app()->environment('production')),
```

Ou plus simple, forcer `true` en defaut :

```php
'secure' => env('SESSION_SECURE_COOKIE', true),
```

**Priorite** : P2

### [SEC-004] Pas d'email verification apres inscription

**Severite** : Moyenne

**Localisation** :

- Fichier : `backend/app/Http/Controllers/AuthController.php:17-63`
- Fichier : `backend/app/Models/User.php` (pas de `MustVerifyEmail`)

**Description** :
Le User model n'implemente pas `MustVerifyEmail`. Apres inscription, le compte est immediatement actif et fonctionnel. Un attaquant peut creer des comptes avec des emails qu'il ne possede pas.

**Impact** :

- Comptes orphelins avec des emails usurpes.
- Pas de canal securise pour la recuperation de mot de passe (si implementee plus tard).
- Spam potentiel si des notifications sont ajoutees.

**Recommandation** :
Accepte comme choix de design pour un MVP si la decision est consciente. Si l'application grandit, implementer `MustVerifyEmail` et un flow de verification email.

**Priorite** : P2

### [SEC-005] Pas de rate limiting sur le login de l'extension (token mode)

**Severite** : Faible

**Localisation** :

- Fichier : `backend/routes/api.php:13`

**Description** :
Les routes auth publiques (register, login, token-login) sont sous `throttle:5,1` (5 requetes par minute). C'est correct, mais le throttle est base sur l'IP. Un attaquant distribue (botnet, IPs rotatifs) peut contourner ce rate limiting pour du brute-force.

Par ailleurs, le login ne renvoie pas le meme message d'erreur pour "email inexistant" et "mot de passe incorrect" — c'est bien, le message est generique `Identifiants invalides`.

**Impact** :
Risque limite grace au rate limiting existant. Le brute-force distribue reste un risque theorique mais difficile a exploiter avec un throttle de 5/min.

**Recommandation** :

- Considerer un account lockout temporaire apres N tentatives echouees par email (pas par IP).
- Optionnel : ajouter un captcha apres 3 echecs.

**Priorite** : P3

### [SEC-006] `selectRaw` dans ApplicationController::stats

**Severite** : Faible

**Localisation** :

- Fichier : `backend/app/Http/Controllers/ApplicationController.php:232-239`

**Description** :

```php
$statusCounts = $user->applications()
    ->selectRaw('status, count(*) as count')
    ->groupBy('status')
    ->pluck('count', 'status');
```

`selectRaw` est utilise avec des chaines statiques (pas d'input utilisateur). C'est securise tel quel. La recherche dans `index()` utilise aussi `whereRaw` avec des parametres lies (le `$search` est bind via `?`), ce qui est correct.

**Impact** :
Aucun impact actuel. Note pour les futurs developpeurs : ne jamais interpoler d'input utilisateur dans les appels `*Raw`.

**Recommandation** :
Aucune action requise. Le code actuel est securise.

**Priorite** : Informationnel

### [SEC-007] Extension popup.js — credentials en memoire

**Severite** : Faible

**Localisation** :

- Fichier : `extension/utils/api.js:42-54`
- Fichier : `extension/utils/storage.js`

**Description** :
Le token d'authentification est stocke dans `chrome.storage.session`, qui est volatile (efface a la fermeture du navigateur). C'est le bon choix pour une extension. Le token n'est jamais ecrit dans `chrome.storage.local` (persistant).

**Impact** :
Aucun — c'est une bonne pratique. Le token est automatiquement efface a la fermeture du navigateur.

**Recommandation** :
Aucune action requise.

**Priorite** : Informationnel

### [SEC-008] Handoff token dans le hash URL — fenetre d'exposition

**Severite** : Faible

**Localisation** :

- Fichier : `extension/utils/api.js:139-181`
- Fichier : `frontend/index.html:8-52`
- Fichier : `frontend/src/stores/authStore.ts:35-40`

**Description** :
Le handoff token est passe dans le fragment hash (`#auth_token=...`), pas dans la query string. Le script inline dans `index.html` le strip immediatement via `history.replaceState`. Le code documente deja le trade-off : une extension malicieuse avec `run_at: document_start` pourrait lire `location.hash` pendant <10ms.

Mitigations en place :

- Token TTL de 60 secondes
- Token one-shot (supprime apres usage cote serveur)
- Ability limitee a `handoff` uniquement
- Verification stricte cote serveur (`count(abilities) === 1`)
- Strip du hash avant tout paint/React mount

**Impact** :
Risque accepte et bien documente. L'attaque requiert une extension malicieuse deja installee sur le meme navigateur, ce qui implique que l'attaquant a deja un niveau d'acces plus eleve.

**Recommandation** :
Aucune action requise — le trade-off est correctement documente et mitige.

**Priorite** : Informationnel

### [SEC-009] Production Docker utilise `php artisan serve`

**Severite** : Faible

**Localisation** :

- Fichier : `Dockerfile:45-48`

**Description** :
Le Dockerfile de production utilise `php artisan serve` (le serveur de developpement PHP integre). Ce serveur :

- Est mono-thread (un seul worker par defaut)
- N'est pas concu pour la production
- Ne gere pas les connexions concurrentes efficacement
- Pas de gestion gracieuse des signaux (SIGTERM)

**Impact** :

- Performances limitees sous charge
- Pas de protection contre les slow-loris attacks
- Pas de timeouts configurables

**Recommandation** :
Pour la production, remplacer par FrankenPHP, RoadRunner ou Nginx + PHP-FPM :

```dockerfile
# Exemple avec FrankenPHP
FROM dunglas/frankenphp
```

Acceptable pour un MVP a faible trafic, mais a migrer avant mise a l'echelle.

**Priorite** : P3

## Bonnes pratiques identifiees

- **IDOR protection** : `ApplicationPolicy` verifie `$user->id === $application->user_id` sur toutes les operations (view, update, delete). Les requetes sont scoped via `$request->user()->applications()`.
- **Input validation** : Toutes les entrees sont validees via des `FormRequest` classes avec des regles strictes (enum validation, max length, URL validation, password complexity avec `uncompromised`).
- **Rate limiting** : Routes publiques a 5/min, routes protegees a 60/min, handoff token a 10/min, export RGPD a 3/min.
- **Security headers** : X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy strict, Permissions-Policy restrictive, HSTS en HTTPS.
- **CSRF protection** : Sanctum SPA mode avec `EnsureFrontendRequestsAreStateful`, XSRF-TOKEN cookie, session regeneration apres login.
- **Password hashing** : Cast `hashed` sur le model User (bcrypt 12 rounds). Validation `uncompromised()` pour verifier les bases de donnees de leaks.
- **RGPD compliance** : Export de donnees, suppression de compte (soft delete), consentement enregistre avec IP et user-agent, pas de scraping automatique.
- **Token security** : Prefix `jt_` pour detection par les scanners de secrets, token expiration a 24h, handoff token 60s one-shot.
- **CORS** : Allowlist explicite par domaine avec patterns regex. `supports_credentials: true` correctement couple avec des origines explicites (pas de `*`).
- **Extension security** : Token volatile (`chrome.storage.session`), HTTPS enforce sur les URLs non-locales, hash URL pour le handoff (pas de query string).
- **Session serialization** : `json` (pas `php`), ce qui protege contre les gadget chain attacks.
- **Separation token/session** : L'extension utilise `Auth::once()` pour eviter de creer des cookies de session, empechant les interferences entre le mode extension et le mode SPA.
- **Sort direction sanitization** : `$sortDirection === 'asc' ? 'asc' : 'desc'` — pas d'injection possible via le parametre de tri.
- **Pagination cap** : `min((int) $request->input('per_page', 50), 100)` — protege contre les requetes de pagination abusives.

## Recommandations generales

1. **Mettre a jour les dependances npm** (Axios, Vite) — correction immediate via `npm audit fix`
2. **Durcir la config session** — defaut `secure: true` pour eviter les oublis en production
3. **Adapter le CSP** pour le SPA — eviter que les styles inline soient bloques en production
4. **Migrer le serveur de production** vers FrankenPHP/Nginx+FPM avant montee en charge
5. **Considerer l'email verification** si l'application sort du stade MVP
